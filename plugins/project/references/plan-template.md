# PROJECT_PLAN.md template

The plan must be executable by a fresh session with no other context. Use this structure; omit a section only if it truly
does not apply (and say so in "Not included"). Tasks are checkboxes so progress survives interruption.

````markdown
# <Project name>: Setup Plan
> Generated by /project:setup on <date>. Execute with `/project:build` or by following the phases below in order.
> Skeleton only: no product features. Tick boxes as you go.

## 1. Context
- **Goal**: ...  **Users**: ...  **Success criteria**: ...
- **Type**: ...  **Constraints**: team, timeline, budget, scale, compliance
- **Working directory**: <abs path>   **Greenfield / existing**: ...

## 2. Decision log
| Topic | Decision | Decided by | Why | Rejected |
(every decision from the interview)

## 3. Tech stack (verified <date>)
| Layer | Tool | Version | Notes |
Runtime, language, framework, DB, cache, queue, test runner, linter, formatter, type checker, CI, container base images, ...

## 4. Prerequisites
Tools to have installed (with `command -v` checks and install hints), accounts, ports that must be free.

## 5. Target structure
```text
<tree with a one-line purpose per top-level entry>
```
Architecture summary: modules, boundaries, dependency direction, how boundaries are enforced. Naming conventions.

## 6. Phases
### Phase 1: Repo & tooling
- [ ] Task: what and exact commands / file contents
  - **Check**: `<command>` → expected result
### Phase 2: Scaffold
### Phase 3: Quality tooling (format, lint, static analysis, hooks, commit convention)
### Phase 4: Proof-of-life slice (one trivial vertical slice, e.g. health endpoint + test) and test setup
### Phase 5: Data & services (DB, migrations, seed, cache, queue, storage, mail, auth skeleton...)
### Phase 6: Containers & dev environment (Dockerfile, compose, devcontainer, task runner, `.env.example`)
### Phase 7: CI/CD (workflows, caching, required checks, release automation, dependency updates, security scans)
### Phase 8: Docs & repo hygiene (README, CONTRIBUTING, SECURITY, LICENSE, ADRs, templates, CODEOWNERS)
### Phase 9: Claude & harness (CLAUDE.md, settings, rules, MCP; harness init, if chosen)
Include full file contents where details matter. Order by dependency.

## 7. Configuration reference
Env vars table (name, purpose, example, required, secret?), ports, service URLs. Mirrors `.env.example`.

## 8. Final verification
Commands that must all pass from a clean checkout, with expected output:
install, format check, lint, static analysis, tests (+ coverage threshold), build, container build/up + health check,
CI config validation, pre-commit hooks fire.

## 9. Manual steps (for the user)
Numbered, in order: what to do, where, why, which phase depends on it. Accounts, secrets, repo creation and push, forge
settings (branch protection, required checks), `/plugin marketplace add` + `/plugin install` (harness), DNS/domains, store accounts.

## 10. Not included (and why)
Consciously skipped topics, e.g. "No cache: no measured need; add when ...".

## 11. Later
Feature ideas and upgrades mentioned during the interview, deliberately out of scope.

## 12. Deviations (filled in during build)
Table: planned vs. actual vs. reason.

## Appendix: full config files
Printed contents of CI workflows, Dockerfile, compose, tool configs, hooks, CLAUDE.md, if too long for the phases.
````

## Writing rules

- Imperative, specific, no pronouns that need context. No "as discussed", "the framework we chose": name it.
- Every command is copy-pasteable and non-interactive (`--yes`, `-y`, flags) where the tool allows; note when interactive input is unavoidable.
- Pin versions that were verified; mark unverified ones "verify at build time".
- Acceptance checks must be objectively checkable (exit code, output string, HTTP status).
- Keep phases independent enough that a failure points to one phase.
